# P158 — separate shell-readable scratch LD_LIBRARY_PATH comparison

P132's original ARM64 executable hardcodes /data/data/com.termux/files/usr/lib, a Termux-style path that the Android emulator's unprivileged ADB shell UID 2000 cannot open even when the root user staged original exact-SHA libraries there (P155: OPEN_PERMISSION_DENIED). That cannot decide whether the original ARM64 Node ELF itself is executable via Native Bridge.

P158 additionally uses **only** /data/local/tmp/dsh-p132-original-node/lib in a disposable, offline Google APIs x86_64 Android emulator. Before a single `--version` invocation, the existing P132 gate attests emulator identity and drops adbd to unprivileged shell UID 2000. P158 revalidates qemu, UID 2000, advertised arm64, guest exact original Node SHA and nine original signed-v138 library SHA values; then uses an environment containing only system PATH and an explicit scratch LD_LIBRARY_PATH. It prints either a strict version token or bounded error class plus output hash (not raw stderr/paths).

P158 is a **separate control experiment**, not a replacement for P155's hardcoded RUNPATH failure and **not** an isolated Android process, original DSH app-UID, EngineManager, production script, or HTTP-ready test. A PASS would prove only that the immutable Node --version ran under shell UID2000 with modified search path. A blocked result may reflect Native Bridge/loader/ABI limitations even if the original hardware ARM64 Node would work. Original installed APK, signature, user phone and P109 permission-deny policy never change. Formal v139 remains BLOCKED.
